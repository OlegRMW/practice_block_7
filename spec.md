# Спецификация v2: два LLM-судьи, единый лимит генерации и ресурсы

Статус: **реализация v2 завершена и проверена в согласованном объёме; полный test запускается пользователем**.
Дата: 2026-11-17.
Ветка: `feature/module_structure`.

## 1. Цель и порядок SDD

Расширить существующий модульный проект: добавить GLM 5.3 Flash к GPT-OSS-120B как второго независимого судью, установить одинаковый максимальный выход Qwen без LoRA и с LoRA — 64 новых токена, сохранять измерения ресурсов обучения/инференса и показывать их в кратком терминальном отчёте.

Эта редакция описывает новую итерацию. Ранее выполненные документы v1 доступны в истории Git. Подготовленные `plan.md` и `tasks.md` относятся к v2 и ожидают подтверждения пользователя.

1. Проанализировать текущий проект, получить уточнения и подготовить этот `spec.md`.
2. После подтверждения спецификации пользователем подготовить новый `plan.md` с архитектурой и техническим планом и `tasks.md` с последовательными задачами.
3. Начать реализацию только после подтверждения плана.
4. Выполнить задачи последовательно и проверить соответствие критериям приёмки.

## 2. Что обнаружено в текущем коде

- Сохраняется структура `configs/`, `scripts/`, `src/text_summary_block_7/`, `tests/`, `results/`, `models/`.
- Три пользовательские точки входа: `train.py`, `evaluate.py`, `report.py`.
- `judge.py` уже содержит общий OpenAI-совместимый клиент RouterAI и проверку JSON, но конфигурация и orchestration рассчитаны на одного судью.
- `ROUTERAI_API_KEY` читается из окружения или корневого `.env`; файл `.env` существует. Значение ключа при анализе не читалось и не выводилось.
- `judge.csv` содержит `judge_model`, `judge_hash` и хеш оценённого ответа. Это позволяет сохранять разные оценки отдельно.
- В `artifacts.rebuild_combined()` используется удаление дубликатов по ID/хешу ответа без учёта судьи: при двух судьях в объединённом CSV останется только одна оценка. Это поведение нужно исправить.
- Текущий report разделяет конфигурации судьи по хешу; в v2 нужно явно показывать название судьи и исключить смешивание его результатов с другими.
- `configs/qwen.yaml` задаёт 64 новых токена для Ollama через `num_predict`; `configs/lora.yaml` задаёт 128 через `max_new_tokens`. Новое требование заменяет прежнее сохранение разных лимитов.
- Полноценных измерений ресурсов сейчас нет: результат Trainer может содержать время/скорость обучения, но отдельного общего сбора RAM/VRAM и ресурсов инференса нет.
- Qwen без LoRA работает в отдельном процессе Ollama; измерение одного Python-процесса не отражает память модели.
- Старые LoRA-метрики рассчитаны по ответам с лимитом 128, а старые записи ресурсов отсутствуют. Эти значения нельзя представить как результаты нового запуска с лимитом 64.
- При начале анализа Git уже показывает изменение `notebooks/main.ipynb`. Это существующее пользовательское изменение; его нельзя отменять или включать в нашу работу.

## 3. Подтверждённые пользователем решения

1. `--llm-as-judge` запускает обоих судей по умолчанию; дополнительный параметр позволяет выбрать одного.
2. Судьи используют один prompt, одинаковые критерии и одну подвыборку из 100 диалогов.
3. Нужны время загрузки и выполнения, скорость, пиковая RAM/VRAM, названия CPU/GPU и размер адаптера; для Ollama учитывается серверный процесс.
4. Энергопотребление, стоимость API и отдельные показатели загрузки CPU/GPU не входят в согласованный набор.
5. После реализации выполняется полный пересчёт test для сравниваемых моделей и оценка обоими судьями: до 600 новых оценок для 3 моделей × 100 диалогов × 2 судьи. Повторы при сетевых ошибках могут увеличить количество технических HTTP-попыток.
6. Для проверки обучения и измерений выполняется короткий реальный LoRA smoke-run, а не полное трёхэпоховое дообучение.
7. Обычный `evaluate.py` заново выполняет инференс. По последующему запросу пользователя добавлено восстановление только пропущенных судейских оценок существующего запуска без пересчёта успешных.
8. Реализация и реальные запуски откладываются до подтверждения спецификации и плана.

## 4. Функциональные требования

### FR-01. Два независимых судьи

Поддерживаются:
- GPT-OSS-120B: `openai/gpt-oss-120b`.
- GLM 5.3 Flash: `z-ai/glm-5.3-flash`.

Оба используют `https://routerai.ru/api/v1`, существующий `ROUTERAI_API_KEY`, один системный prompt и критерии faithfulness, coverage, relevance, coherence — целые оценки 1–5. Overall вычисляется как среднее четырёх критериев. По последнему уточнению пользователя report выводит средние по запускам каждого судьи отдельно и общую среднюю двух судей с равными весами.

Общая работа с API и валидация выделяются из выбора/перебора судей. Не требуется создавать две копии логики запросов. Конкретные модули и схема конфигурации определяются в плане.

### FR-02. Конфиги и CLI

- YAML позволяет задавать набор судей и общие/индивидуальные параметры запросов без хранения секретов.
- Без `--llm-as-judge` не создаётся клиент судьи, не выполняются его API-запросы, ключ для обычного инференса/report не требуется.
- С `--llm-as-judge` по умолчанию вызываются оба судьи; отдельный CLI-параметр позволяет выбрать только одного из них.
- Выбор неизвестного судьи или противоречивые аргументы обнаруживаются до инференса/API.
- Сохраняются путь `--config`, именованные аргументы, `--set` и их существующий приоритет. Примеры точного синтаксиса выбора судьи приводятся в плане.
- Относительные YAML-пути считаются от файла YAML, CLI-пути — от рабочего каталога.
- Старые результаты должны читаться; совместимость прежних пользовательских конфигов либо явная инструкция их обновления описывается в плане и README.

### FR-03. Общая выборка и разделение результатов

- Инференс и BLEU/ROUGE — весь test, по умолчанию 1500 строк.
- LLM-судьи — одна детерминированная подвыборка из 100 строк с seed 42 по умолчанию. На меньшем проверочном dataset используется весь доступный объём.
- Объём подвыборки и seed настраиваются через конфиг/CLI.
- Оба судьи оценивают идентичные тексты предсказаний, диалогов и эталонов.
- Каждая оценка однозначно связана с суммаризирующей моделью, ID диалога, хешем ответа, идентификатором/настройками судьи и запуском.
- В индивидуальных и объединённых CSV сохраняются оценки обоих судей; одна не вытесняет другую и не теряет сведения о происхождении.
- Ошибка одного судьи не стирает успешные оценки и не мешает попробовать второго. Частичные ошибки видны отдельно, итоговый код команды отражает неполное выполнение.
- Исторические оценки GPT-OSS остаются доступны с прежней маркировкой. Оценка другого текста не присваивается текущему ответу. Отсутствие оценки GLM не заменяется нулём.
- Повторный запуск с флагом судьи выполняет новые оценки выбранных судей; запуск без него сохраняет прежние оценки.

### FR-04. Максимум 64 новых токена

- В поставляемых конфигах Qwen3-0.6B и Qwen3-0.6B + LoRA задан одинаковый `generation.max_new_tokens: 64`.
- Ollama получает соответствующий `num_predict=64`, Transformers/Unsloth — `max_new_tokens=64`.
- Это верхняя граница, а не требование генерировать ровно 64 токена: модель может завершить ответ раньше по EOS.
- Существующая возможность явного изменения параметров через CLI сохраняется; в результатах фиксируется фактически применённый лимит.
- Лимиты ответов LLM-судей настраиваются независимо: требование 64 относится к моделям суммаризации.
- Остальные prompts, baseline, условия LoRA-обучения и backend без отдельной необходимости не меняются.
- Изменение конфига не изменяет старые метрики задним числом: новый полный инференс формирует новые результаты.

### FR-05. Измерение ресурсов

Для новых запусков сохраняются:

| Показатель | Требуемая область |
| --- | --- |
| Время загрузки/подготовки модели, с | Обучение и инференс отдельно от основной фазы |
| Время основной фазы, с | Реальное обучение либо генерация test-ответов |
| Скорость | Обучение — примеров/с; инференс — ответов/с и новых токенов/с |
| Пиковая RAM, MiB | Измеряемые процессы приложения/модели с указанием области |
| Пиковая VRAM, MiB | Область измерения GPU/процесса/backend указана явно |
| CPU/GPU | Идентификация использованного оборудования, не только факт наличия GPU |
| Размер адаптера, MiB | Для LoRA, с определённым составом измеряемых файлов |
| Условия запуска | Модель/backend, режим/precision при доступности, объём работы, лимит генерации и ID запуска |

Уточнения к измерениям:
- Измерения обучения относятся к LoRA; Baseline и zero-shot помечаются как не проходившие обучение.
- Ресурсы инференса не включают время LLM-судей и расчёта BLEU/ROUGE.
- Токены/с считаются по фактически сгенерированным токенам, а не по лимиту 64 или числу слов.
- Для Ollama необходимо учитывать сервер и процесс исполнения модели; память Python-клиента нельзя выдавать за память модели.
- Если Ollama работает удалённо либо ОС/backend не предоставляет достоверных данных, недоступный показатель отображается как `N/A` с причиной, без выдуманного значения.
- Общая память GPU с другими приложениями не называется памятью конкретной модели.
- Наблюдаемый пик при периодическом измерении обозначается как измеренный/выборочный, а не гарантированный абсолютный аппаратный максимум.
- Warm/cold load и переиспользование модели у Ollama должны быть различимы, если влияют на интерпретацию времени загрузки.
- Размер адаптера отличается от размера всей базовой модели и от размера checkpoints.
- Полное обучение и короткий smoke-run явно различаются по объёму, шагам и режиму.

### FR-06. Краткий report

- `report.py` остаётся отдельным read-only сценарием: не запускает обучение, инференс или API.
- Выводит компактные таблицы качества BLEU/ROUGE, независимые средние GPT-OSS и GLM по запускам, общую среднюю с равными весами судей, ресурсы обучения и инференса.
- Название судьи показывается явно; одних хешей недостаточно.
- Показаны число обработанных/оценённых примеров, пропуски/ошибки, исторический статус и фактические условия запусков.
- Результаты с разными лимитами генерации, выборками или объёмом обучения не изображаются как полностью сопоставимые.
- Старые ресурсы не восстанавливаются из предположений и показываются как отсутствующие.
- По 1500 строк в терминал не выводятся: индивидуальные метрики и замеры остаются в артефактах.
- `evaluate.py` сохраняет прогресс и короткое сообщение о результате, без больших таблиц.
- Отчёт связывает ресурсные показатели с соответствующим запуском/адаптером, а не произвольно с последним файлом другой модели.

### FR-07. Пересчёт и документация

После реализации пункты 1–2 выполняются пользователем; исполнитель проводит короткие интеграционные проверки и пункты 3–6:
1. Выполнить реальный инференс Baseline, Qwen и Qwen LoRA на полном test; для обеих Qwen использовать лимит 64.
2. Получить новые оценки каждого из двух судей для той же подвыборки 100 диалогов каждой модели.
3. Выполнить короткий реальный LoRA smoke-run с измерениями и проверкой сохранения/загрузки адаптера. Не подменять его результатами исходного полного обучения.
4. Обновить новые производные артефакты вне защищённых каталогов.
5. Обновить README: конфиги, выбор судей, лимит, ресурсные показатели/единицы и краткие таблицы актуальных результатов.
6. Зафиксировать фактически выполненные проверки и ограничения в отчёте верификации.

## 5. Нефункциональные требования

- **NFR-01 — сохранность:** вся папка `notebooks/` и исходные CSV в `data/` остаются побайтово неизменными относительно начала итерации v2. Существующее пользовательское изменение notebook не откатывается. Проверка сохранности учитывает игнорируемые Git файлы.
- **NFR-02 — модульность:** конфигурация, работа с судьями, сохранение/чтение результатов, измерение ресурсов и представление отчётов разделены по ответственности. Конкретная архитектура — в плане после подтверждения spec.
- **NFR-03 — безопасность секретов:** используется существующий ключ из окружения/`.env`; его значение не записывается в артефакты, CLI-примеры, логи и спецификации.
- **NFR-04 — воспроизводимость:** параметры генерации, выборки, судей и измерений привязаны к запуску; сравнение допускает проверку происхождения данных.
- **NFR-05 — измеримость:** единицы, интервалы/область измерений и недоступные значения явны; сбор статистики не добавляет синхронизацию после каждого токена без необходимости.
- **NFR-06 — зависимости:** Poetry и lock-файл сохраняются; новые библиотеки ресурсного мониторинга, если нужны, объявляются явно. Целевая проверенная среда — Windows/NVIDIA/Ollama.
- **NFR-07 — автономность отчёта:** report работает по сохранённым артефактам без GPU, запущенной Ollama и API-ключа.
- **NFR-08 — отказоустойчивость:** частичные ошибки судей/мониторинга не превращаются в успешные нулевые оценки и не уничтожают ранее успешные результаты.
- **NFR-09 — тестируемость:** тесты двух судей, общей выборки, отсутствия API без флага, сохранения обеих оценок, лимитов и ресурсных отчётов не требуют сотен платных запросов; отдельно проводятся реальные согласованные проверки.

## 6. Ограничения и исключения

- Ветка работы — `feature/module_structure`.
- До подтверждения плана меняются только документы SDD; код, конфиги, CSV, notebook, веса и зависимости на этом этапе не меняются.
- Новые и ранее созданные производные результаты в `results/` могут обновляться после разрешения реализации; исходные CSV и `notebooks/` не изменяются.
- Произвольная оценка сторонних готовых ответов не добавляется; разрешён точечный repair существующего запуска через `--retry-failed`.
- Новые модели суммаризации, другой baseline, новые задачи обучения и полный fine-tuning не входят в задачу.
- Энергопотребление, стоимость API, проценты загрузки CPU/GPU и отдельный dashboard не входят в согласованный объём.
- Лимит 64 выравнивает максимальную длину ответа, но не делает Ollama и Unsloth идентичными по quantization, prompts и условиям выполнения; отчёт не должен утверждать такую идентичность.
- API-запуски и полный пересчёт разрешены пользователем как часть реализации, но не выполняются до SDD-подтверждений.

## 8. Подтверждения и следующий шаг

### Последнее согласованное уточнение

- План подтверждён, реализация разрешена. Полный test и массовые API-запросы пользователь запускает сам; исполнителю нужны только небольшие реальные проверки и команды запуска.
- Каждый evaluate заново генерирует ответы и создаёт уникальный ID запуска. Снимки ответов, метрик и ресурсов сохраняются отдельно и не перезаписывают прежние запуски.
- Для каждого ответа создаётся широкий CSV `scores_by_run.csv`: отдельные столбцы всех критериев каждого судьи для каждого запуска, например `run_<id>__gpt_oss__faithfulness`. BLEU/ROUGE также сохраняются по запускам.
- Report усредняет успешные полные запуски одного судьи по общим ID диалогов, затем усредняет результаты двух судей с равным весом. Запуски с разными условиями генерации/адаптерами не смешиваются, неполные отмечаются и не включаются в среднее.
- Разные тексты ответов разных запусков допустимы: это среднее качество модели по запускам, а не повторная оценка одного неизменного ответа. Без API старые оценки не копируются в новый запуск как новый голос.
