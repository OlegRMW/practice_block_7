- `README.md` пуст; зависимости и упаковка описаны в `pyproject.toml`, используется Poetry.
- Основная логика находится в `notebooks/main.ipynb`; также существует `notebooks/eda.ipynb`.

- CSV предсказаний содержат исходные данные и колонки `baseline_summary`, `qwen_summary`, а файл LoRA также `qwen_lora_summary`.
- CSV LLM-судьи содержат `index`, `model`, четыре оценки и `overall`; устойчивый `id` диалога в них отсутствует. Для использования этих результатов необходимо согласовать и проверить связь `index` с исходной выборкой.

- Данные, модели и CSV исключаются текущим `.gitignore`. Поэтому одной проверки `git diff` недостаточно для подтверждения их неизменности.

### Логика notebook

1. **Baseline:** NLTK `sent_tokenize`, выбор первого и последнего предложения при числе предложений больше двух, очистка маркеров `#PersonN#:`. Соединение первого и последнего предложений без дополнительного разделителя сохраняется по прямому указанию пользователя.
2. **Qwen Zero-shot:** Ollama, модель `qwen3:0.6b`, `think=False`, `temperature=0`, `num_predict=64`, `num_ctx=2048`, системный prompt из notebook.
3. **Qwen LoRA:** `Qwen/Qwen3-0.6B`, Unsloth, длина 2048, без 4-битной загрузки; LoRA `r=16`, `alpha=16`, `dropout=0`, семь attention/MLP target-модулей, seed 42.
4. **Дообучение:** 3000 случайных обучающих примеров с seed 42, отдельный validation CSV, prompt/completion dataset, `completion_only_loss=True`, 3 эпохи, batch size 1, accumulation 8, learning rate `1e-4`, cosine scheduler. Полный набор параметров находится в ячейках подготовки данных и `SFTConfig`.
5. **Инференс LoRA:** chat template без thinking, `max_new_tokens=128`, `do_sample=False`, декодирование только продолжения.
6. **Метрики:** `evaluate` с ROUGE и SacreBLEU; сейчас вычисляются для выборки целиком, а не для каждого ответа.
7. **LLM-as-judge:** OpenAI-совместимый клиент RouterAI, `openai/gpt-oss-120b`, ключ из `ROUTERAI_API_KEY`; faithfulness, coverage, relevance, coherence — целые числа 1–5, overall — их среднее. В notebook используется до 100 случайных диалогов с seed 42 и пропуск ранее оценённых пар `(index, model)`.

Перечисленное описывает существующее поведение, а не автоматически утверждённые настройки нового CLI.

## 3. Функциональные требования

### FR-01. Самостоятельный пакет

Бизнес-логика переносится в импортируемый пакет в `src/`. Скрипты используют модули пакета; выполнение или динамический импорт notebook для работы приложения не требуется.

### FR-02. Конфигурация и CLI

- Конфиги располагаются в `configs/`, по аналогии с эталоном используют YAML.
- В конфиг выносятся пути данных и результатов, выбор моделей, настройки генерации, базовой модели, LoRA, дообучения, оценки и судьи.
- Скрипт принимает путь к конфигу. Параметры из конфига можно переопределить при запуске без редактирования файла.
- Приоритет: явные именованные CLI-аргументы выше `--set`, значения `--set` выше выбранного YAML. Неуказанные CLI-аргументы не затирают конфиг значениями по умолчанию парсера.
- Поддерживаются обычные именованные аргументы, например `--learning-rate 0.0002`, и общий `--set ключ.вложенный_ключ=значение` для остальных вложенных настроек. Изменение параметра при запуске не изменяет сам YAML.
- Относительные пути в YAML разрешаются относительно самого YAML по аналогии с эталоном. Относительные пути из CLI, включая `--set`, считаются от текущего рабочего каталога.
- Вызовы LLM-судьи разрешаются только явным флагом `--llm-as-judge` скрипта `evaluate.py`; включить их через YAML или `--set` нельзя.
- Некорректные ключи, типы и значения обнаруживаются до загрузки модели или обращения к API.
- API-ключи берутся из окружения/`.env` и не включаются в конфиги, отчёты или логи.

### FR-03. Запуск суммаризации

Предусмотрены ровно три пользовательских скрипта по аналогии с эталоном:

- `train.py` — LoRA-дообучение.
- `evaluate.py` — инференс выбранной модели на test, расчёт её метрик, сохранение CSV и короткое сообщение о результате без таблиц.
- `report.py` — сравнение Baseline, Qwen Zero-shot и Qwen LoRA по сохранённым CSV.

Отдельный `predict.py` и режим одиночного диалога не требуются согласованным сценарием. Инференс и BLEU/ROUGE выполняются на всём test.

Для LoRA загружаются базовая модель и адаптер. Использование уже сохранённого адаптера не должно требовать повторного дообучения.

### FR-04. Только LoRA-дообучение

- Отдельный тренировочный скрипт выполняет дообучение с LoRA, без обучения модели с нуля и без полного fine-tuning базовых весов.
- Подготовка данных, prompts, target-модули и параметры обучения извлекаются из `main.ipynb`; изменения поведения перечисляются и согласуются.
- Используются отдельные train и validation CSV, тестовые данные не участвуют в обучении.
- Сохраняются адаптер, токенизатор и эффективные настройки запуска, позволяющие воспроизвести загрузку и параметры дообучения.
- Объём выборки, seed, настройки обучения и путь сохранения управляются конфигом/CLI.

### FR-05. Оценка и CSV

- Отдельный сценарий `evaluate` создаёт или обновляет CSV результатов оценки.
- Для каждого оцениваемого ответа сохраняются идентификатор диалога, модель, предсказание, эталон и метрики BLEU, ROUGE и LLM-as-judge.
- Новые CSV создаются и обновляются в отдельной папке результатов вне `notebooks/` и вне путей исходных датасетов; имя папки будет определено в плане.
- Повторный `evaluate.py` пересчитывает результаты выбранной модели и обновляет её производные CSV в папке результатов; новая версия заменяет прежние результаты этой модели, сохраняя результаты остальных моделей.
- Без `--llm-as-judge` выполняются только инференс, BLEU/ROUGE и вывод имеющихся судейских оценок; API-ключ судьи не требуется, API-запросов нет.
- С `--llm-as-judge` после инференса дополнительно заново оцениваются 100 диалогов для выбранной модели через API. Размер судейской подвыборки и seed настраиваются; значение по умолчанию — 100 и 42. Если в проверочном dataset меньше 100 строк, оцениваются все доступные строки.
- Ранее полученные судейские оценки сохраняются независимо от нового инференса. При совпадении модели, диалога, эталона и предсказания показываются как соответствующие текущему ответу; при несовпадении показываются отдельно как исторические и не смешиваются с текущей сводкой. Новые API-оценки заменяют текущие оценки соответствующих ответов, сохраняя возможность показать старые результаты как исторические.
- Повторный `report.py` перечитывает CSV и пересчитывает сравнительные таблицы без генерации ответов и запросов к судье.
- Во время реализации после согласования плана нужно подготовить исходный файл метрик всех трёх моделей по имеющимся CSV, чтобы сравнение работало до нового инференса. Численные метрики пересчитываются по предсказаниям; имеющиеся оценки судьи переносятся только при подтверждённом соответствии. Недостающие оценки не выдумываются.
- Существующие CSV нельзя изменять ни непосредственно, ни при запуске новых скриптов. Вся папка `notebooks/` остаётся без изменений, включая файлы результатов и сохранённые модели.
- Старые CSV судьи нельзя присоединять к ответам только по позиции без проверки соответствия; отсутствие подтверждённой связи должно быть явно обозначено.

### FR-06. Метрики качества

- BLEU и ROUGE вычисляются отдельно для каждого ответа.
- Вычисляются ROUGE-1/2/L/Lsum в шкале 0–1, SacreBLEU для каждого ответа в шкале 0–100 и отдельный корпусный BLEU в сводке. Корпусный BLEU не подменяется средним sentence BLEU. Настройки расчёта сохраняются с результатами.
- BLEU/ROUGE вычисляются на всём test. LLM-as-judge вызывается только с флагом `--llm-as-judge` и только для подвыборки из 100 диалогов с seed 42 по умолчанию. При одинаковых входных test и настройках подвыборка одинакова для сравниваемых моделей.
- Сохраняются RouterAI `https://routerai.ru/api/v1`, модель `openai/gpt-oss-120b`, prompt и параметры запросов из `main.ipynb`. Критерии: faithfulness, coverage, relevance, coherence — целые 1–5, `overall` — среднее четырёх оценок.
- Ошибку API, отсутствие оценки и невалидный JSON нельзя представлять как успешную нулевую оценку.

### FR-07. Отдельный отчёт

- Отдельный скрипт строит отчёт о качестве каждой модели исключительно из содержимого CSV.
- Отчёт выводится в терминале в виде читаемых таблиц с понятными названиями колонок; HTML или Markdown отчёт не требуются.
- По уточнению пользователя терминальные таблицы выводятся только скриптом `report.py` и содержат краткую сводку по моделям. BLEU/ROUGE и оценки судьи каждого ответа сохраняются в CSV, построчная детализация в терминал не выводится.
- Отчёт показывает размер выборок и число успешных оценок судьи отдельно по моделям. Исторические судейские оценки, если есть, выводятся отдельно с указанием происхождения и соответствующей версии ответов.
- Построение отчёта не вызывает модели, не обращается к LLM-судье и не запускает обучение.
- Отсутствующие оценки и неполные данные показываются явно; отчёт не должен создавать видимость полной оценки по неполной выборке.

### FR-08. Документация

README описывает назначение папок, установку через Poetry, конфиги и overrides, необходимые ресурсы, загрузку адаптера, сценарии запуска/дообучения/оценки/отчёта, форматы CSV и ограничения среды.

## 4. Нефункциональные требования

- **NFR-01 — сохранность:** содержимое существующих CSV и всей папки `notebooks/` остаётся неизменным. Контроль файлов выполняется хешированием, включая игнорируемые Git файлы; новые артефакты также не записываются в `notebooks/`.
- **NFR-02 — разделение ответственности:** CLI отвечает за аргументы и запуск; загрузка данных, модели, обучение, оценка, конфиги и отчётность отделены в модули.
- **NFR-03 — воспроизводимость:** сохраняются seed, фактические параметры, идентификаторы модели/адаптера/судьи и сведения, необходимые для сопоставления метрик с ответами. Полная детерминированность GPU и внешнего API не обещается.
- **NFR-04 — диагностируемость:** ошибки конфигурации, отсутствующих файлов, адаптера, ресурсов NLTK и внешних сервисов понятны пользователю; провал команды не маскируется успешным завершением.
- **NFR-05 — автономность отчёта:** генерация отчёта по готовым CSV работает без GPU, Ollama и API-ключа судьи.
- **NFR-06 — зависимости:** сохраняются Poetry и пакетная структура `src/`; необходимые изменения зависимостей документируются. Проверка проводится в доступной локальной среде Windows с учётом требований Unsloth, NVIDIA GPU и Ollama. Поддержка иных ОС отдельно не запрашивалась.
- **NFR-07 — проверяемость:** критические правила CLI/config, запрет перезаписи исходных CSV, расчёт метрик, валидация судьи и связь ответов с оценками проверяются без полного обучения модели.

## 5. Ограничения и границы

- Работа ведётся в локальной ветке `feature/module_structure`.
- Существующие CSV не редактируются, не перезаписываются и не удаляются. Их перемещение не предполагается без отдельного согласования.
- Вся папка `notebooks/` используется только для чтения; `main.ipynb` служит источником логики и не исполняется в ходе рефакторинга. Новые модели, checkpoints, CSV и кеши сохраняются вне этой папки.
- До подтверждения спецификации и плана не создаются реализация, новые конфиги и рабочие CLI-скрипты.
- Обучение с нуля, полный fine-tuning и добавление новых моделей сверх согласованного набора не входят в задачу.
- Baseline переносится буквально, включая склейку предложений. Prompts и различающиеся параметры генерации zero-shot и LoRA сохраняются из notebook.
- Пользователь подтвердил необходимость работающих LoRA-дообучения и внешнего API. После утверждения плана проводятся реальные проверки этих путей на небольшом объёме; проверки только с заглушками недостаточны. Полное трёхэпоховое обучение для проверки не требуется.

## 6. Критерии приёмки

Критерии основаны на согласованных требованиях.

1. **AC-01:** ветка правильная; исходные CSV и содержимое папки `notebooks/` совпадают до и после работ и проверочных запусков; новых файлов в `notebooks/` нет.
2. **AC-02:** папки `configs/`, `scripts/`, `src/<пакет>/` организованы по принципам эталона; рабочий CLI не зависит от notebook.
3. **AC-03:** один запуск с YAML и другой с CLI override демонстрируют изменение заданного параметра; файл YAML остаётся неизменным. Ошибка неизвестного параметра обнаруживается до затратного запуска.
4. **AC-04:** согласованные модели генерируют summary через сценарий запуска; LoRA-инференс использует сохранённый адаптер без повторного обучения.
5. **AC-05:** реальный короткий LoRA smoke-run обновляет только параметры адаптера, сохраняет артефакты вне `notebooks/` и допускает их последующую загрузку.
6. **AC-06:** `evaluate` формирует CSV с индивидуальными метриками каждой пары «диалог–модель» в выбранной области оценки. Повторный запуск соблюдает согласованную политику обновления и не изменяет исходные CSV.
7. **AC-07:** `report.py` выводит только сводные терминальные таблицы сравнения трёх моделей по подготовленным CSV; индивидуальные метрики доступны в CSV. Модели и API при этом не вызываются. После нового `evaluate.py` таблицы отражают обновлённые результаты выбранной модели.
8. **AC-08:** ошибки судьи и отсутствующие оценки явно отражены; такие строки не учитываются как успешно оценённые.
9. **AC-09:** README позволяет повторить сценарии с конфигом и CLI overrides; результаты проверок сопоставлены с требованиями, а недоступные в среде проверки явно перечислены.
10. **AC-10:** реальный запрос к RouterAI проходит через перенесённый код, результат валидируется и сохраняется; инференс на test сообщает число обработанных ответов и каталог результатов без таблиц.
11. **AC-11:** без `--llm-as-judge` не создаётся API-клиент судьи, не требуется его ключ и не выполняются запросы. Старые оценки доступны для вывода; оценка другого текста не приписывается текущему ответу. С флагом судья вызывается для согласованной подвыборки.

## 7. Согласованные уточнения
