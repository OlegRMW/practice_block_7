## 1. Структура проекта

Сохраняем пакет `text_summary_block_7`, Poetry и принципы эталонного проекта: YAML, тонкие CLI-обёртки, функциональные модули в `src/`.

`results/` и `models/` создаются при реализации/запусках. Существующие модели из `notebooks/models/` можно загрузить только для чтения; новые результаты обучения записываются в `models/`. Кеши направляются вне `notebooks/`.

## 2. Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| `config.py` | YAML, схема и валидация, CLI overrides, разрешение путей, эффективные настройки |
| `data.py` | Чтение датасетов, проверка колонок/ID, детерминированная подвыборка |
| `preprocessing.py` | Prompt/completion dataset, prompts и chat template из notebook |
| `models.py` | Общий интерфейс генерации и baseline с буквальным сохранением алгоритма |
| `neural.py` | Ollama zero-shot, загрузка Qwen с сохранённым LoRA, генерация |
| `train.py` | Unsloth/LoRA/SFTTrainer, seed, сохранение адаптера и токенизатора |
| `evaluate.py` | Инференс test, метрики, необязательный судья, сохранение и короткое сообщение без таблиц |
| `metrics.py` | Индивидуальные и сводные BLEU/ROUGE, явные параметры расчёта |
| `judge.py` | RouterAI, исходный prompt, JSON-валидация, четыре оценки и overall |
| `artifacts.py` | Безопасные пути записи, CSV/manifest, хеши ответов, атомарная публикация файлов |
| `reports.py` | Чтение CSV, только сводные терминальные таблицы, исторические оценки |
| `bootstrap.py` | Однократная подготовка начальных результатов из существующих CSV при реализации |

CLI-скрипты разбирают аргументы, вызывают пакет, выводят понятные ошибки и возвращают код завершения. Тяжёлые зависимости загружаются внутри нужного пути выполнения: `report.py` не импортирует Unsloth, Torch, Ollama или OpenAI. Не допускается создание API-клиента судьи без соответствующего флага.

## 3. Конфиги и интерфейс CLI

Три самостоятельных YAML соответствуют трём вариантам модели. Разделы:

- `seed` — 42 по умолчанию.
- `data` — пути train/test/validation, имена колонок.
- `paths` — каталоги новых моделей и результатов.
- `model` — вид, имя модели, адрес Ollama либо путь адаптера.
- `generation` — исходные prompts, thinking и параметры генерации соответствующего backend.
- `lora`, `training` — только для дообучаемой модели; параметры из notebook.
- `metrics` — параметры ROUGE/SacreBLEU.
- `judge` — endpoint, имя модели, имя переменной окружения, prompt, timeout, retries, sample size 100 и seed 42; без API-ключа и без переключателя автоматического запуска.

Приоритет: YAML → повторяемый `--set` → явно указанные именованные флаги. Неизвестные ключи и невалидные значения отвергаются. Повтор одного ключа в `--set` использует последнее значение. Пути YAML считаются от его каталога, CLI-пути — от текущего каталога; происхождение переопределённых путей учитывается при разрешении.

Основные именованные аргументы:

- Общие: `--config`, повторяемый `--set`.
- `train.py`: `--learning-rate`, `--epochs`, `--train-size`, `--output-dir` для нового адаптера.
- `evaluate.py`: `--test`, `--adapter-path`, `--output-dir` для корня результатов, `--llm-as-judge`, `--judge-sample-size`.
- `report.py`: `--results-dir`, `--models` для отбора моделей; по умолчанию показывает все найденные согласованные модели.

Модель для инференса выбирается конфигом. Любой иной разрешённый параметр доступен через `--set`. `--set judge.enabled=true` не должен обходить необходимость явного флага судьи.

Предполагаемые команды после реализации:

```powershell
poetry run python scripts/train.py --config configs/lora.yaml --learning-rate 0.0002
poetry run python scripts/evaluate.py --config configs/baseline.yaml
poetry run python scripts/evaluate.py --config configs/qwen.yaml
poetry run python scripts/evaluate.py --config configs/lora.yaml --adapter-path notebooks/models/qwen3_summary_lora
poetry run python scripts/evaluate.py --config configs/lora.yaml --llm-as-judge
poetry run python scripts/report.py --results-dir results
```

Для обычного запуска `lora.yaml` ссылается на новый выходной адаптер в `models/`; существующий адаптер из notebook выбирается явно, как в примере. До обучения или выбора существующего адаптера отсутствие файла объясняется ошибкой.

## 4. Хранение результатов и связь оценок

Для каждого ключа `baseline`, `qwen`, `qwen_lora` создаётся собственный каталог `results/<model>/`:

| Файл | Содержимое |
| --- | --- |
| `predictions.csv` | `id`, `dialogue`, `reference`, `prediction`, `model`, `run_id`, `response_hash` |
| `metrics.csv` | `id`, `model`, `run_id`, `response_hash`, sentence BLEU и ROUGE-1/2/L/Lsum каждого ответа |
| `summary.csv` | `model`, `run_id`, число ответов, корпусный BLEU, средние индивидуальные BLEU/ROUGE |
| `judge.csv` | `id`, `model`, `response_hash`, четыре критерия, overall, judge model/prompt hash, время, статус и ошибка, источник оценки |
| `run.yaml` | Эффективный конфиг без секретов, параметры метрик, источники/хеши входа и сведения об артефактах |

Начальные результаты всех моделей дополнительно собираются в `results/all_models_metrics.csv`: единая таблица индивидуальных BLEU/ROUGE и подтверждённых судейских оценок. Она является производным представлением и обновляется после успешного инференса; источником последующих отчётов служат согласованные CSV моделей. Исторические оценки в текущие строки не подставляются.

`response_hash` учитывает модель, диалог, эталон и предсказание с однозначной сериализацией. Совпадение `id` само по себе недостаточно. Судейские результаты хранятся отдельно от перезаписываемых предсказаний, поэтому запуск без судьи их не удаляет. Повторная оценка того же ответа заменяет актуальную запись по ключу ответа и конфигурации судьи; оценки других версий ответа остаются историческими. При нескольких конфигурациях судьи показывается происхождение и не смешиваются их агрегаты.

Обновления сначала готовятся во временных файлах в каталоге результатов. Отчёт проверяет совпадение `run_id`/числа строк/ключей и не принимает частично опубликованный набор. Ошибка генерации не должна заменять прежний полный результат неполным. Ошибки судьи сохраняются как ошибки без численной оценки; успешные ответы сохраняются по мере выполнения, чтобы не потерять уже оплаченные результаты.

Защита записи проверяет разрешённый абсолютный путь до создания файлов: запрещены `notebooks/`, существующие исходные CSV, каталоги исходных данных и пути через симлинки/junctions в защищённые области. `--output-dir` не может отключить эту защиту.

## 5. Потоки выполнения

### Дообучение

1. Прочитать и проверить конфиг, пути и train/validation.
2. Проверить доступность GPU/нужных библиотек; явно сообщить о невозможности запустить Unsloth.
3. Загрузить базовую Qwen, присоединить обучаемый LoRA, проверить набор обучаемых параметров.
4. Подготовить 3000 случайных train-примеров и validation по notebook; размер train управляется параметром. Слишком большой явно заданный размер не урезается молча.
5. Запустить SFTTrainer с исходными значениями по умолчанию, сохранить адаптер, токенизатор и настройки вне `notebooks/`.

### Инференс без судьи

1. Прочитать конфиг и test, проверить колонки, уникальные непустые ID и тексты; не терять строки молча.
2. Получить summary выбранной модели для каждой строки test в исходном порядке.
3. Вычислить индивидуальные BLEU/ROUGE и корпусный BLEU, сохранить новые результаты.
4. Прочитать прежние оценки судьи, если есть, сопоставить по хешам и показать текущие и исторические отдельно.
5. Вывести число обработанных ответов и путь сохранения, без таблиц. Отсутствие ключа RouterAI не мешает запуску. Импорт зависимостей метрик проверяется до генерации, чтобы неисправность окружения не обнаруживалась после долгого инференса.

### Инференс с судьёй

Выполнить предыдущий сценарий и дополнительно оценить детерминированную выборку `min(100, len(test))` с seed 42. Выборку формировать по каноническому порядку test, одинаково для всех моделей. С флагом выполнить новые запросы, даже если оценки уже были. Повторные попытки, timeout и параметры запроса сохранить из notebook. Проверить JSON и целые оценки 1–5, вычислить overall. При частичном провале показать число ошибок и вернуть ненулевой код, сохранив успешно рассчитанные метрики и судейские ответы.

### Сравнительный отчёт

`report.py` только читает CSV и строит:

1. Сводку BLEU/ROUGE по моделям с размерами выборок и понятными шкалами.
2. Таблицу четырёх критериев судьи и overall с количеством актуальных оценок.
3. При наличии — отдельную сводку исторических оценок с источником и статусом соответствия.

По уточнению пользователя построчные таблицы не выводятся: индивидуальные значения остаются в CSV. `evaluate.py` таблиц не печатает.

Для читаемого терминального вывода использовать `rich` (явная зависимость) и разделить широкие таблицы по группам метрик. Пропуски отображать как `—`, а не как нули. Неполные наборы и разные выборки явно обозначать; отсутствующие модели не изображать оценёнными.

## 6. Метрики и начальные CSV

ROUGE считать через `rouge-score`, SacreBLEU — через `sacrebleu`, избегая загрузки исполняемых metric-модулей из сети. Индивидуальные ROUGE — F1; сводка — среднее по ответам. Для ROUGE-Lsum использовать разделение предложений NLTK и явно документировать подготовку. Sentence BLEU: `tokenize=13a`, `smooth_method=exp`, `effective_order=True`; корпусный BLEU считать отдельно с `effective_order=False`. Настройки зафиксировать в manifest и README. Кратко объяснить, почему sentence BLEU и corpus BLEU не равны.

После реализации модулей однократно вызвать внутреннюю функцию `bootstrap.py`: прочитать исходные test/predictions/judge CSV, проверить соответствие `id`, текстов и порядка, пересчитать численные метрики и сформировать `results/`. Это подготовительная операция разработки, а не четвёртый пользовательский CLI и не скрытое действие `report.py`.

Проверить связь старого `index` с test и соответствующим файлом предсказаний; для судьи RouterAI использовать прежде всего `routerai_judge_results.csv`, так как выбран именно этот API. Если исходные CSV не доказывают, какой текст оценивался, сохранять оценки как исторические с непроверенной связью; не назначать им искусственно текущий хеш. Начальные актуальные оценки получать реальным явным запуском судьи там, где восстановление невозможно. Источники и границы достоверности указать в отчёте проверки.

Существующий `.gitignore` игнорирует CSV. Для подготовленных результатов сделать узкие исключения для нужных CSV в `results/`; не включать исходные данные, секреты, веса или кеши. Так начальный отчёт сохранится вместе с проектом. Объём и состав отслеживаемых результатов проверить перед завершением.
