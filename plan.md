## 3. Конфигурация и CLI

### Судьи

В трёх YAML заменить одиночный `judge.model` на именованные модели:

```yaml
judge:
  base_url: https://routerai.ru/api/v1
  api_key_env: ROUTERAI_API_KEY
  prompt: "<существующий prompt без изменений>"
  timeout: 120.0
  max_retries: 2
  temperature: 0
  max_tokens: 1000
  sample_size: 100
  seed: 42
  models:
    gpt_oss:
      model: openai/gpt-oss-120b
    glm_flash:
      model: z-ai/glm-5.3-flash
```

Внутри записи судьи допускаются индивидуальные `timeout`, `max_retries`, `temperature`, `max_tokens`; неуказанные берутся из общего раздела. Prompt, выборка и критерии общие и не переопределяются отдельно для судьи.

Имена CLI — `gpt_oss`, `glm_flash`; в CSV сохраняется также полный идентификатор модели. Список выбранных судей не заменяет факт явного разрешения API:

- Без `--llm-as-judge`: только инференс/BLEU/ROUGE/ресурсы.
- С `--llm-as-judge`: оба судьи из конфига.
- С `--llm-as-judge --judges glm_flash`: только GLM.
- `--judges` без `--llm-as-judge`, неизвестное имя или пустой список — ранняя ошибка.

Совместимость: старые CSV продолжают читаться. Старый формат YAML с одиночным `judge.model` отклоняется понятной ошибкой с инструкцией перехода на `judge.models`; поставляемые конфиги обновляются одновременно. Автоматически добавлять платного второго судью в старый пользовательский конфиг не будем.

### Генерация и ресурсы

- В `qwen.yaml` и `lora.yaml` — `generation.max_new_tokens: 64`.
- Backend получают соответственно `num_predict=64` и `max_new_tokens=64`.
- Явные overrides сохраняются; использованные значения записываются в manifest.
- Добавить раздел `resources` с `sample_interval_seconds: 0.2`. Интервал — положительное число; фактическое значение сохраняется с измерениями.
- Сохраняются правила приоритетов YAML → `--set` → именованные CLI-аргументы и происхождения путей.
- Для публикации ресурсной записи обучения добавить в `train.py` `--results-dir`, переопределяющий существующий `paths.results_dir`. `--output-dir` по-прежнему означает каталог адаптера.

Команды после реализации:

```powershell
poetry run python scripts/evaluate.py --config configs/qwen.yaml
poetry run python scripts/evaluate.py --config configs/qwen.yaml --llm-as-judge
poetry run python scripts/evaluate.py --config configs/lora.yaml --adapter-path notebooks/models/qwen3_summary_lora --llm-as-judge --judges glm_flash
poetry run python scripts/report.py
```

Ключ берётся из прежнего `ROUTERAI_API_KEY` в окружении/`.env`, не передаётся в CLI и не сохраняется в документах/результатах.

## 4. Результат генерации и одинаковый лимит

Ввести небольшой тип `GenerationResult` с полями:
- `text`;
- `generated_tokens` либо отсутствие значения с причиной;
- `backend`;
- дополнительные backend-тайминги и идентификация модели.

Ollama: брать `eval_count`, `eval_duration`, `load_duration`, `prompt_eval_duration` из ответа, наносекунды переводить в секунды. LoRA: считать реальные output token IDs после длины prompt, включая сгенерированный EOS, и явно указать это правило. Baseline не имеет генеративного токенизатора — токеновая скорость `N/A`; скорость ответов и RAM доступны.

Результат отделяет текст, необходимый BLEU/ROUGE, от измерений; нельзя вычислять токены по словам или считать каждый ответ равным лимиту 64. Алгоритм baseline, prompts обеих Qwen и семантика stop/EOS сохраняются.

## 5. Судьи, ошибки и сохранение

`judging.py` один раз выбирает 100 строк с seed 42 и передаёт одни и те же записи выбранным судьям. Запросы идут последовательно, с существующими timeout/retry; дополнительных параллельных исполнителей и многопоточных платных запросов не требуется.

`judge.py` отвечает за общий клиент и один запрос. Ошибка инициализации/ответа отдельного судьи записывается и не останавливает попытку запуска второго; глобально отсутствующий ключ выявляется до затратного инференса при явном флаге API. Секреты и полные provider exception с возможными credentials не сохраняются.

Ключ оценки: суммаризирующая модель + ID + response hash + judge model + judge config hash. Время/ID попытки позволяют отличить повторные обращения. Повторный успешный запрос обновляет актуальную оценку выбранного судьи; неуспешный не удаляет прежний успех. Число уникальных успешно оценённых ответов и число последних ошибок показываются отдельно, без двойного счёта одной пары.

Старые `legacy_unverified` записи сохраняются как исторические. Оценки со старым хешем ответа не включаются в текущую сводку. Оба судьи используют прежние четыре критерия 1–5; overall — среднее внутри одной оценки.

Платные успехи сохраняются после каждого ответа. Полный перезапуск evaluate остаётся повторным инференсом. По последующему запросу пользователя добавлен ограниченный recovery: `recovery.py` читает snapshot конкретного run ID, вычисляет недостающие пары и вызывает только их, затем обновляет judge snapshot и производные CSV. Существующие успешные оценки не запрашиваются повторно; нового run ID/голоса не создаётся. Пустые/невалидные ответы повторяются до `--judge-attempts` (по умолчанию 3), при прежних настройках судьи; сохраняются безопасные диагностики.

### Объединённый CSV

`metrics.csv` и `summary.csv` каждой модели остаются независимыми от числа судей.

`all_models_metrics.csv` становится длинной таблицей:
- для оценённого ответа — отдельная строка на судью/конфигурацию с идентификаторами, критериями, статусом/происхождением;
- для неоценённого ответа — одна строка с пустыми судейскими полями;
- BLEU/ROUGE могут повторяться в строках двух судей; report берёт их из исходных `metrics/summary.csv`, поэтому средние не получают двойной вес.

На 4500 ответах и двух оценках для 100 ответов каждой модели ожидается 4800 строк объединённого представления при одной актуальной конфигурации каждого судьи. Проверка определяется ключами, а не только количеством строк.

## 6. Измерения ресурсов

### Границы и единицы

Использовать `time.perf_counter()` и периодический сбор с интервалом 0.2 с. Сохранять отдельные фазы подготовки/загрузки и основной работы. Для CUDA синхронизировать границы таймера, не каждый токен.

- Обучение: загрузка/подготовка, затем `trainer.train()`; сохранение артефактов не входит в время обучения.
- LoRA-инференс: staging/загрузка/подготовка, затем генерация всего test.
- Baseline: подготовка, затем суммаризация; GPU не используется.
- Вызовы LLM-судей и расчёт BLEU/ROUGE не входят в ресурсные показатели генерации.

Точность peak при периодическом сборе обозначается явно. Все объёмы — MiB (2^20 bytes), время — секунды. На недоступных счётчиках — пустое значение плюс причина; в report — `N/A`.

### RAM, GPU, оборудование

- RAM: psutil, наблюдаемый максимум суммы RSS целевого процесса и выбранных дочерних процессов. Указать PID/область; сумма RSS не называется уникальной физической памятью из-за возможных общих страниц.
- Torch: `max_memory_allocated` и `max_memory_reserved` по использованным CUDA-устройствам, с reset пиков на границах фаз. Эти счётчики не называются всей занятой памятью GPU.
- Ollama на локальном адресе: обнаружить процесс сервера по слушающему порту и его runner-процессы, динамически учитывать появляющихся детей. RAM клиента записывать отдельно. При неоднозначном обнаружении/нескольких моделях область и ограничение явно указать.
- VRAM Ollama: при доступности NVML — выборочный максимум памяти связанных GPU-процессов. При WDDM/недоступном process memory — `N/A` с причиной.
- Дополнительно сохранить `size_vram` выбранной модели из `/api/ps` как память размещённой модели; это отдельный показатель, не замена измеренного peak.
- Удалённая Ollama: серверные RAM/peak VRAM и оборудование не определяются по локальному компьютеру; сохраняются доступные API-сведения, прочее `N/A`.
- Общая память GPU с посторонними приложениями не используется вместо памяти модели.
- CPU: модель из ОС; GPU — реально использованное устройство из Torch/NVML и сведения о размещении у Ollama, если доступны. Наличие GPU в системе не означает, что backend использовал её.

Добавить явные зависимости `psutil` и `nvidia-ml-py`, согласовать lock-файл. Инициализация NVML необязательна для работы приложения и не ломает CPU/report.

### Время и скорость Ollama

Создание Client не загружает модель. Поэтому:
- время подготовки Python-клиента хранится отдельно;
- загрузка модели берётся из `load_duration` запросов;
- сохраняются полное клиентское время фазы и время без сообщённой сервером загрузки, с явно указанным способом расчёта;
- токены/с для основного сравнения — фактические токены / время основной фазы;
- серверная скорость decode = сумма `eval_count` / сумма `eval_duration` — отдельный показатель;
- список работающих моделей до первого запроса позволяет отметить warm/cold/unknown; новую загрузку нельзя выдавать за warm-run.

Отсутствующие backend-тайминги не заменяются нулём. При невозможности корректно выделить время без загрузки показатель помечается недоступным, полное измеренное wall time сохраняется.

### Условия обучения и адаптер

Записать число train/validation-примеров, выполненные шаги/эпохи, batch/accumulation, trainable parameters, precision и `run_kind=smoke|full`. Скорость — фактически обработанные примеры/время либо документированный счётчик Trainer.

Размер адаптера: сумма файла весов адаптера и `adapter_config.json`, без базовой модели, tokenizer и checkpoints. Идентификатор адаптера определяется хешами весов/конфига.

Ресурсы короткого нового smoke-адаптера не присваиваются существующему полноценно обученному адаптеру из notebooks. В report это отдельная строка обучения; для старого адаптера при отсутствии достоверных ресурсов остаётся `N/A`.

## 7. Артефакты и совместимость

```text
results/
  baseline/
    predictions.csv, metrics.csv, summary.csv, judge.csv, run.yaml
    resources.csv
  qwen/
    predictions.csv, metrics.csv, summary.csv, judge.csv, run.yaml
    resources.csv
  qwen_lora/
    predictions.csv, metrics.csv, summary.csv, judge.csv, run.yaml
    resources.csv
  training/<training_run_id>/
    resources.csv
    run.yaml
  all_models_metrics.csv
models/<adapter>/
  adapter weights, adapter_config.json, tokenizer files
  training-run.yaml
```

Каждая ресурсная строка содержит `run_id`, `operation`, `phase`, модель/backend, adapter ID при наличии, оборудование, число примеров/токенов/шагов, времена/скорости, память и методы/причины отсутствия. Manifest получает schema version, эффективные настройки и связь inference → adapter → training run, когда она доказана.

Report читает только сохранённые данные; старые manifests/CSV без ресурсов остаются поддержаны. Неполное обновление файлов обнаруживается через ID/schema/проверку ключей, не маскируется как завершённый запуск. Безопасные пути записи остаются обязательными.

Исторические результаты текущей итерации до полного пересчёта сохраняются в локальном verification-каталоге. Защищённые исходные CSV не мигрируются. Текущие derived CSV в `results/` обновляются, а оценки исторических ответов продолжают храниться в `judge.csv`.

## 8. Терминальный report

Компактные группы таблиц:
1. BLEU и ROUGE по суммаризирующим моделям.
2. Отдельная сводка GPT-OSS-120B и отдельная GLM 5.3 Flash с числом успешных оценок/ошибок.
3. При наличии — короткие исторические сводки, отдельно от текущих.
4. Ресурсы инференса: время загрузки/работы, ответы/с, токены/с, RAM/VRAM и методы.
5. Ресурсы обучения: run kind, размер работы, время/скорость, память, размер адаптера.
6. Условия/оборудование и краткие причины `N/A`, чтобы не делать одну чрезмерно широкую таблицу.

Названия судей видны полностью, а не только хеши. На одну модель/фазу/конфигурацию — одна строка сводки. Строки ответов и PID-сэмплы в терминал не печатаются.

Проверять совпадение test ID/hash, лимита генерации и идентичность судейской подвыборки; при различиях отмечать ограниченную сопоставимость. Различия precision/backend/prompts сохраняются как условия, а не объявляются устранёнными из-за лимита 64.

## 9. Проверки и полный пересчёт

Порядок после подтверждения плана:
1. Зафиксировать новые SHA-256 и список защищённых файлов на начало v2, включая уже изменённый пользователем notebook. Старый snapshot v1 не использовать для отката.
2. Реализовать и проверить конфиги/лимиты, нескольких судей, CSV и ресурсные измерения на fixtures.
3. Реально проверить короткое обучение с ресурсами и инференс сохранённого smoke-адаптера.
4. Реально проверить обоих судей на малой выборке, исключить ошибки интеграции до полного платного прогона.
5. Последовательно запустить полный Baseline, Qwen и Qwen LoRA на test с фиксацией ресурсов; обе Qwen — 64.
6. Для полного LoRA test использовать существующий обученный адаптер из notebooks через изолированную копию, а не одношаговый smoke-адаптер.
7. Получить 100 оценок каждого судьи для каждой из трёх моделей — 600 успешных оценок; ошибки не объявлять завершёнными. Проверить независимость, полноту и одинаковую выборку.
8. Проверить запуск без флага API, чтение старых артефактов, актуальные таблицы и полное отсутствие изменений защищённых файлов.
9. Обновить README с двумя судьями, лимитом, единицами/методами ресурсов и новыми сводными числами. Обновить `verification.md` и матрицу AC.

Автотесты используют fake clocks/processes/API и не расходуют деньги. Реальные измерения могут дать документированное `N/A` там, где ОС/backend не поддерживает счётчик. Нельзя выдумывать пропущенные метрики или восстанавливать ресурсы старого полного обучения из smoke-run.
